# 02 - Frame Format v1

Status: Draft
Version: 1.0-draft.2

This document defines the bytes a sensor transmits and receives over LoRa: layout,
frame types, keys, rotating tags, encryption, frame counters, and the downlink
structure. Reading encodings are in 03 (Payload v1); the pairing procedure,
including the key exchange that produces session keys, is in 04.

## 1. Goals (informative)

- A proxy can validate, deduplicate and route a frame without any key.
- Only the owner's server can read a frame, or create one a sensor will accept.
- An observer cannot link frames from one device across hours.
- Small: 22 bytes of overhead.

## 2. Layout

```
Offset  Size  Field
0       1     magic      0xC5
1       1     ver_type   version (high nibble) | type (low nibble)
2       4     net_tag    rotating network tag
6       4     dev_tag    rotating device tag
10      4     fcnt       frame counter (uint32)
14      N     ciphertext AES-128-CCM encryption of the payload, 1 <= N <= 64
14+N    8     mic        CCM authentication tag
```

Bytes 0-13 are the header. The header is authenticated (it is the CCM associated
data) but not encrypted.

## 3. Field rules

- `magic` MUST be `0xC5`.
- `version` MUST be `1` for this specification.
- The plaintext payload MUST be between 1 and 64 bytes. Every frame is therefore
  between 23 and 86 bytes long.
- Receivers MUST discard frames shorter than 23 or longer than 86 bytes.

## 4. Frame types

The high bit of the type nibble gives the direction: `0x1`-`0x7` are uplinks,
`0x8`-`0xF` are downlinks. `0x0` is reserved and MUST NOT be sent.

| Type | Name | Direction | Confirmed | Tags |
|---|---|---|---|---|
| `0x1` | `DATA` | Uplink | No | Normal |
| `0x2` | `DATA_CONFIRMED` | Uplink | Yes | Normal |
| `0x3` | `HEARTBEAT` | Uplink | No | Normal |
| `0x4` | `HEARTBEAT_CONFIRMED` | Uplink | Yes | Normal |
| `0x5` | `JOIN` | Uplink | Yes | Bootstrap |
| `0x6` | `SYNC` | Uplink | Yes | Bootstrap |
| `0x7` | reserved | Uplink | - | - |
| `0x8` | `DOWNLINK` | Downlink | - | Normal or bootstrap |
| `0x9`-`0xF` | reserved | Downlink | - | - |

- *Confirmed* means the sensor expects a `DOWNLINK` that answers it (section 10)
  and retries if none arrives (08, Sensor behavior).
- *Normal* tags are computed as in section 6. *Bootstrap* tags are both
  `00000000`; see section 11.
- `HEARTBEAT` frames carry periodic status. Servers use them for supervision
  (07). A sensor SHOULD send a confirmed heartbeat often enough to keep its clock
  within the tag window (section 6.3).

## 5. Keys

### 5.1 Device keys

Each sensor has, from manufacture or flashing:

- `dev_eui`: 8-byte permanent identifier. It MUST be unique and MUST NOT be sent
  in the clear.
- `k_root`: 16-byte random key. It MUST be generated by a cryptographically
  secure random number generator and MUST be unique per device.

`dev_eui` and `k_root` reach the server through the pairing QR code (04).

A device always uses one *key set*: a pair `k_enc`, `k_dev_tag` derived from a
base key:

```
k_enc     = HKDF-SHA256(ikm = base, salt = dev_eui, info = "cs1 enc", L = 16)
k_dev_tag = HKDF-SHA256(ikm = base, salt = dev_eui, info = "cs1 tag", L = 16)
```

- The *root key set* uses `base = k_root`. It is used only for `JOIN` and the
  `DOWNLINK` that answers it.
- The *session key set* uses `base = k_session` (5.3). It is used for every other
  frame.

### 5.2 Network keys

Each server has a 16-byte random network key `k_net` per network. It never
leaves the server.

```
k_net_route = HKDF-SHA256(ikm = k_net, salt = none, info = "cs1 route", L = 16)
```

The server gives `k_net_route` to each sensor in a `SET_NETWORK` command
(section 10.3), always under the session key set. Proxies and relays never
receive any key.

### 5.3 Session key

`k_session` is created at every pairing by an X25519 exchange (RFC 7748) carried
in `JOIN` and the `KEY_EXCHANGE` command. With `sensor_pub` and `server_pub` the
two 32-byte ephemeral public keys:

```
shared    = X25519(own_ephemeral_private, peer_ephemeral_public)
k_session = HKDF-SHA256(ikm = shared, salt = k_root,
                        info = "cs1 session" | dev_eui | sensor_pub | server_pub,
                        L = 16)
```

- Both sides MUST reject an all-zero `shared` value and abandon the exchange.
- Ephemeral private keys MUST be freshly generated for each `JOIN`, MUST NOT be
  stored once `k_session` is derived, and MUST NOT be reused.
- Because `k_root` is the HKDF salt, only a party holding the pairing code can
  complete the exchange. Because the exchange is ephemeral, someone who holds
  the pairing code but did not take part cannot derive `k_session` later.

The procedure and its states are defined in 04.

## 6. Epochs and tags

### 6.1 Tags

```
epoch   = floor(unix_time / 3600)
net_tag = trunc32(HMAC-SHA256(k_net_route, "net" | uint32(epoch)))
dev_tag = trunc32(HMAC-SHA256(k_dev_tag,   "dev" | uint32(epoch)))
```

A sensor MUST compute tags from its own clock at the time it builds the frame.
A retransmission (section 8.3) that crosses an epoch boundary keeps its original
tags, because it is the same bytes.

### 6.2 Reserved value

A computed tag equal to `00000000` collides with the bootstrap value. A sensor
whose computed `net_tag` or `dev_tag` is `00000000` MUST use `00000001` instead,
and servers MUST apply the same substitution when building tag tables.

### 6.3 Server tag window

The server MUST recognize tags for epochs `e - 1`, `e` and `e + 1`, where `e` is
its current epoch. A sensor whose clock is off by more than about an hour is not
recognized and has to resynchronize with `SYNC` (section 11.2).

### 6.4 Collisions

Tags are 32 bits, so two devices can share a tag in an epoch. A server MUST try
every device whose tags match, and accept the frame for the first device whose
MIC verifies.

## 7. Encryption

```
nonce = dev_eui | uint32(fcnt) | dir        (13 bytes)
dir   = 0x00 for uplink types, 0x01 for downlink types
aad   = frame[0:14]                         (the whole header)
ciphertext | mic = AES-128-CCM-Encrypt(k_enc, nonce, plaintext, aad), tag length 8
```

`fcnt` in the nonce is the uplink counter for uplinks and the downlink counter
for downlinks (section 8). Because `dir` separates the two, the counters may hold
the same value without nonce reuse.

## 8. Frame counters

### 8.1 Uplink counter

- Each sensor has one uplink counter `fcnt` across all uplink types. It starts at
  1 and increases by one for each new frame.
- A sensor MUST NOT send two different frames with the same `fcnt`, ever. This
  includes after a reboot, a battery change, a factory reset, or re-pairing to a
  different network.
- The counter MUST NOT wrap. A sensor that reaches `0xFFFFFFFF` MUST stop
  transmitting. (At one frame per minute this takes over 8000 years.)

### 8.2 Persistence by reservation

To avoid writing flash on every frame, a sensor reserves counter values in
blocks:

1. Flash holds `reserved`, the first counter value not yet reserved.
2. Before using a value `v` where `v >= reserved`, the sensor MUST write
   `reserved = v + B` to flash and confirm the write.
3. On boot, the sensor MUST set its next counter to the stored `reserved` and
   then reserve a new block.

`B` is the block size. It SHOULD be 64. A boot therefore skips up to `B` values,
which is harmless.

`reserved` MUST survive a factory reset.

### 8.3 Retransmission

A confirmed uplink that is not answered is retransmitted as exactly the same
bytes: same `fcnt`, same tags, same ciphertext. It is not a new frame and does not
use a new counter value, but it is a new transmission: the first retry comes at
least 4 seconds after the original (08 section 5). Proxies and the server
therefore tell transmissions apart by time, not by bytes: copies received within
2 seconds of a transmission's first copy are that transmission, and a later copy
is a retransmission that MUST reach the server and be answered again (section
8.5).

### 8.4 Downlink counter

- The server keeps a downlink counter `fcnt_down` per device, starting at 1 after
  pairing and increasing by one per downlink frame it builds.
- The server MUST persist it with the same reservation scheme as 8.2.
- A sensor MUST discard a downlink whose `fcnt_down` is not greater than the last
  one it accepted since its last `JOIN`.
- A sensor resets its stored last-accepted `fcnt_down` to 0 when it sends `JOIN`,
  and the server resets the device's `fcnt_down` when it accepts a `JOIN`.

### 8.5 Server acceptance of uplinks

For each device the server keeps `last_fcnt`, the highest accepted uplink
counter, and a record of which of the 16 counter values below it were received.

- `fcnt > last_fcnt`: accept, and update `last_fcnt`. Any gap is allowed.
- `last_fcnt - 16 < fcnt <= last_fcnt` and not yet received: accept (late
  arrival).
- Otherwise: treat as a duplicate or replay. Do not deliver it again. If it is a
  retransmission (section 8.3) of a confirmed type, the server MUST answer it
  again, within the limits of 07 section 4, step 5, so a sensor that missed the
  first answer stops retrying.

A frame is accepted only after its MIC verifies.

## 9. Uplink payload

```
Offset  Size  Field
0       1     uflags
1       N     readings (03, Payload v1), 0 <= N <= 63
```

`uflags` bits:

| Bit | Name | Meaning |
|---|---|---|
| 0 | `DL_ACK` | The sensor accepted a downlink containing commands since its previous uplink |
| 1 | `TIME_UNSURE` | The sensor's clock has not been set by a downlink since boot |
| 2-7 | reserved | MUST be 0 when sent, MUST be ignored when received |

## 10. Downlink payload

### 10.1 Layout

```
Offset  Size  Field
0       4     reply_to     fcnt of the uplink this downlink answers
4       4     server_time  server's Unix time when the downlink was built
8       1     dflags
9       M     commands     zero or more commands, M <= 55
```

`dflags` bits:

| Bit | Name | Meaning |
|---|---|---|
| 0 | `PENDING` | The server has more downlinks queued; the sensor SHOULD send an uplink soon |
| 1-7 | reserved | MUST be 0 when sent, MUST be ignored when received |

### 10.2 Sensor acceptance

A sensor MUST accept a downlink only if all of the following hold:

1. It arrived in an RX window of the sensor's most recent uplink.
2. The MIC verifies.
3. `reply_to` equals the `fcnt` of that most recent uplink.
4. `fcnt_down` is greater than the last accepted one (8.4).

Binding every downlink to the uplink it answers means old downlinks cannot be
replayed, even into a sensor that has just been reset.

On accepting a downlink, the sensor:

- MUST set its clock to `server_time`.
- MUST treat a confirmed uplink as acknowledged.
- MUST execute the commands in order.
- MUST set `DL_ACK` in its next uplink if the downlink contained at least one
  command.

### 10.3 Commands

Each command is a type-length-value entry:

```
cmd_id (uint8) | len (uint8) | args (len bytes)
```

A sensor MUST skip a command it does not know, using `len`. Commands MUST be
idempotent, because the server re-sends any command whose downlink was not
followed by an uplink with `DL_ACK`.

| `cmd_id` | Name | Args | Effect |
|---|---|---|---|
| `0x01` | `SET_NETWORK` | `k_net_route` (16) | Store the network routing key and use normal tags from now on |
| `0x02` | `SET_HEARTBEAT` | `uint16` minutes, 1-1440 | Change the heartbeat interval |
| `0x03` | `LEAVE` | none | Erase `k_net_route`, return to unpaired state (counters are kept) |
| `0x04` | `KEY_EXCHANGE` | `server_pub` (32) | Complete the X25519 exchange (5.3) and switch to the session key set |
| `0x05`-`0x3F` | reserved | | Future network commands |
| `0x40`-`0x7F` | application | | Defined in 03 (Payload v1) and by device profiles |
| `0x80`-`0xFF` | reserved | | |

## 11. Bootstrap frames

`JOIN` and `SYNC` use bootstrap tags (`net_tag = dev_tag = 00000000`), because the
sensor either has no network key or does not trust its clock. The server
identifies the device by trying keys (11.3).

### 11.1 `JOIN`

Sent by a sensor that has no session, normally when the user presses its button
during pairing. It is encrypted under the root key set. Its payload is:

```
uflags (1, TIME_UNSURE set) | sensor_pub (32)
```

The server answers with a `DOWNLINK` under the root key set, with bootstrap
tags, containing `KEY_EXCHANGE`. Nothing else may be sent under the root key
set. The full pairing procedure is in 04.

### 11.2 `SYNC`

Sent under the session key set, in three situations:

- immediately after `KEY_EXCHANGE`, to fetch `SET_NETWORK` (04);
- by a paired sensor whose clock is unknown, for example after the batteries were
  removed;
- by a paired sensor that has had no answer to confirmed uplinks for a long time
  (threshold in 08).

Its payload is `uflags` optionally followed by readings. The server answers with a
`DOWNLINK` with bootstrap tags. Its `server_time` sets the sensor's clock, after
which the sensor uses normal tags again.

### 11.3 Server identification of bootstrap frames

- For `JOIN`: the server tries the root key set of each device that is waiting to
  be paired (scanned but not yet joined).
- For `SYNC`: the server tries the session key set of each device that is paired
  or in the middle of pairing.
- The server MUST limit how many bootstrap frames it processes per minute, so
  that a flood of bootstrap frames cannot use unbounded CPU. 50 per minute is
  RECOMMENDED.

### 11.4 Federation limit (informative)

Bootstrap frames carry no network tag, so a relay cannot route them to an owner.
A sensor that only a neighbor's proxy can hear can resynchronize only if its
owner subscribes to bootstrap frames on the relay (09). Owners SHOULD place at
least one of their own proxies within range of every sensor during pairing.

## 12. Proxy rules

A proxy has no keys. For each received LoRa packet it MUST:

1. Discard it if it is shorter than 23 or longer than 86 bytes, if `magic` is not
   `0xC5`, or if `version` is not 1.
2. Discard it if its type is `0x0` or a downlink type (`0x8`-`0xF`). Proxies hear
   each other's downlinks and MUST NOT forward them.
3. Discard it if the exact same bytes were forwarded within the deduplication
   window (RECOMMENDED 2 s). The window MUST be shorter than 4 seconds, so a
   retransmission (section 8.3) is always forwarded.
4. Forward it unchanged, with reception metadata, as defined in 05 (Proxy
   envelope).

Proxies MUST forward uplink types they do not recognize (`0x7`), so new frame
types work without proxy updates.

## 13. Security considerations

| Concern | How v1 handles it |
|---|---|
| Forged frames | AES-CCM with a 64-bit tag and a per-device key |
| Replay of uplinks | Counter rules in 8.5 |
| Replay of downlinks | `reply_to` binding and downlink counter (10.2) |
| Nonce reuse | Counters never repeat (8.1, 8.2); direction byte separates uplink and downlink |
| Tracking a device over time | Hourly tags; `dev_eui` never in the clear |
| Linking via counter values | Not addressed in v1. `fcnt` is in the clear and increases steadily, so an observer can link a device's frames across epochs by counter continuity. A future version may mask it. |
| Key compromise | Per device. A leaked pairing code lets an attacker who is present during a future pairing interfere with it, but does not reveal any past or future session that it did not take part in (5.3). |
| Second-hand devices | A previous owner who kept the pairing code cannot read traffic after the device is paired again. They can attempt an active attack during that pairing; owners who need protection from that should re-flash `k_root`. |
| Proxy dropping frames | Out of scope for the frame format; handled by path diversity and supervision (07) |

The 64-bit MIC gives a forgery probability of 2^-64 per attempt, which is far
below what LoRa airtime allows an attacker to try.
