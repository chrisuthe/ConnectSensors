# 02 - Frame Format v1

Status: Draft
Version: 1.0-draft.3

This document defines the bytes a sensor transmits and receives over LoRa: layout,
frame types, keys, rotating tags, encryption, frame counters, and the downlink
structure. Reading encodings are in 03 (Payload v1); the pairing procedure,
including the key exchange that produces session keys, is in 04.

## 1. Goals (informative)

- A proxy can validate, deduplicate and route a frame without any key.
- Only the owner's server can read a frame, or create one a sensor will accept.
- An observer cannot link frames from one device across hours, or group the
  devices of one network.
- Only the holder of a device's keys can prove which tags are the device's.
- Small: 22 bytes of overhead.

## 2. Layout

```
Offset  Size  Field
0       1     magic      0xC5
1       1     ver_type   version (high nibble) | type (low nibble)
2       8     tag        rotating key-fingerprint tag (section 6)
10      4     fcnt       frame counter (uint32)
14      N     ciphertext AES-128-CCM encryption of the payload, 1 <= N <= 64
14+N    8     mic        CCM authentication tag
```

Bytes 0-13 are the header. The header is authenticated (it is the CCM associated
data) but not encrypted.

## 3. Field rules

- `magic` MUST be `0xC5`.
- `version` MUST be `1` for this specification.
- The plaintext payload MUST be between 1 and 64 bytes. Every frame is therefore
  between 23 and 86 bytes long.
- Receivers MUST discard frames shorter than 23 or longer than 86 bytes.

## 4. Frame types

The high bit of the type nibble gives the direction: `0x1`-`0x7` are uplinks,
`0x8`-`0xF` are downlinks. `0x0` is reserved and MUST NOT be sent.

| Type | Name | Direction | Confirmed | Tags |
|---|---|---|---|---|
| `0x1` | `DATA` | Uplink | No | Normal |
| `0x2` | `DATA_CONFIRMED` | Uplink | Yes | Normal |
| `0x3` | `HEARTBEAT` | Uplink | No | Normal |
| `0x4` | `HEARTBEAT_CONFIRMED` | Uplink | Yes | Normal |
| `0x5` | `JOIN` | Uplink | Yes | Bootstrap |
| `0x6` | `SYNC` | Uplink | Yes | Bootstrap |
| `0x7` | reserved | Uplink | - | - |
| `0x8` | `DOWNLINK` | Downlink | - | Normal or bootstrap |
| `0x9`-`0xF` | reserved | Downlink | - | - |

- *Confirmed* means the sensor expects a `DOWNLINK` that answers it (section 10)
  and retries if none arrives (08, Sensor behavior).
- *Normal* tags are derived from the epoch, *bootstrap* tags from the frame
  counter (section 6.1). A `DOWNLINK` carries the tag of the uplink it answers.
- `HEARTBEAT` frames carry periodic status. Servers use them for supervision
  (07). A sensor SHOULD send a confirmed heartbeat often enough to keep its clock
  within the tag window (section 6.3).

## 5. Keys

### 5.1 Device keys

Each sensor has, from manufacture or flashing:

- `dev_eui`: 8-byte permanent identifier. It MUST be unique and MUST NOT be sent
  in the clear.
- `k_root`: 16-byte random key. It MUST be generated by a cryptographically
  secure random number generator and MUST be unique per device.

`dev_eui` and `k_root` reach the server through the pairing QR code (04).

A device always uses one *key set*: a pair `k_enc`, `k_dev_tag` derived from a
base key:

```
k_enc     = HKDF-SHA256(ikm = base, salt = dev_eui, info = "cs1 enc", L = 16)
k_dev_tag = HKDF-SHA256(ikm = base, salt = dev_eui, info = "cs1 tag", L = 16)
```

- The *root key set* uses `base = k_root`. It is used only for `JOIN` and the
  `DOWNLINK` that answers it.
- The *session key set* uses `base = k_session` (5.3). It is used for every other
  frame.

### 5.2 No network key

There is no network-wide key. A frame's tag is derived from the device's own key
set (section 6), so devices of one network share nothing an observer can see.
Proxies and relays never receive any key.

### 5.3 Session key

`k_session` is created at every pairing by an X25519 exchange (RFC 7748) carried
in `JOIN` and the `KEY_EXCHANGE` command. With `sensor_pub` and `server_pub` the
two 32-byte ephemeral public keys:

```
shared    = X25519(own_ephemeral_private, peer_ephemeral_public)
k_session = HKDF-SHA256(ikm = shared, salt = k_root,
                        info = "cs1 session" | dev_eui | sensor_pub | server_pub,
                        L = 16)
```

- Both sides MUST reject an all-zero `shared` value and abandon the exchange.
- Ephemeral private keys MUST be freshly generated for each `JOIN`, MUST NOT be
  stored once `k_session` is derived, and MUST NOT be reused.
- Because `k_root` is the HKDF salt, only a party holding the pairing code can
  complete the exchange. Because the exchange is ephemeral, someone who holds
  the pairing code but did not take part cannot derive `k_session` later.

The procedure and its states are defined in 04.

## 6. Epochs and tags

### 6.1 Tags

A frame's `tag` is the fingerprint of an Ed25519 public key (RFC 8032) derived
from the device's key set:

```
epoch = floor(unix_time / 3600)
index = "e" | uint32(epoch)               normal frames
      | "b" | uint32((fcnt - 1) / 64)     bootstrap frames (JOIN, SYNC)
seed  = HMAC-SHA256(k_dev_tag, "cs1 tag seed" | index)       32 bytes
pub   = Ed25519 public key for the private key seed (RFC 8032 section 5.1.5)
tag   = trunc64(SHA-256("cs1 tag fp" | pub))
```

- `k_dev_tag` is from the key set the frame is sent under (5.1): the root key
  set for `JOIN`, the session key set for every other uplink.
- The block size 64 is the reservation block of 8.2. `fcnt` starts at 1 and
  each boot starts on a reservation boundary, so one bootstrap tag covers the
  counter values of one block: 1-64, 65-128, and so on.
- A `DOWNLINK` carries the tag of the uplink it answers, whichever key set it
  is sent under. A sensor does not check a downlink's tag; the MIC and
  `reply_to` decide (10.2).

A sensor MUST compute a normal tag from its own clock at the time it builds the
frame. A retransmission (section 8.3) that crosses an epoch boundary keeps its
original tag, because it is the same bytes.

Properties (informative):

- Without `k_dev_tag`, tags are unpredictable and unlinkable across epochs and
  blocks, and devices of one network share nothing.
- The holder of `k_dev_tag` can derive `seed`, so it can prove a tag is its own
  by signing with the key behind `pub` (09). Someone who only saw the tag would
  need a 64-bit SHA-256 preimage to find a usable `pub`.
- A sensor generates one Ed25519 public key per epoch in which it transmits, and
  one per block while it sends bootstrap frames. It never signs. It SHOULD
  compute the next epoch's tag before the epoch boundary, so a frame sent just
  after the boundary does not wait for it.
- `fcnt` is in the clear, so a block-wide bootstrap tag adds no linkability.

### 6.2 No reserved value

Every 8-byte value is a valid tag, including all zeros. Senders and servers use
the computed value as it is.

### 6.3 Server tag window

The server MUST recognize normal tags for epochs `e - 1`, `e` and `e + 1`, where
`e` is its current epoch. A sensor whose clock is off by more than about an hour
is not recognized by its normal tags and has to resynchronize with `SYNC`
(section 11.2).

### 6.4 Collisions

Two devices can share a tag. With `T` live tags the chance of any collision is
about `T^2 / 2^65`. A server MUST try every device whose tags match, and accept
the frame for the first device whose MIC verifies.

## 7. Encryption

```
nonce = dev_eui | uint32(fcnt) | dir        (13 bytes)
dir   = 0x00 for uplink types, 0x01 for downlink types
aad   = frame[0:14]                         (the whole header)
ciphertext | mic = AES-128-CCM-Encrypt(k_enc, nonce, plaintext, aad), tag length 8
```

`fcnt` in the nonce is the uplink counter for uplinks and the downlink counter
for downlinks (section 8). Because `dir` separates the two, the counters may hold
the same value without nonce reuse.

## 8. Frame counters

### 8.1 Uplink counter

- Each sensor has one uplink counter `fcnt` across all uplink types. It starts at
  1 and increases by one for each new frame.
- A sensor MUST NOT send two different frames with the same `fcnt`, ever. This
  includes after a reboot, a battery change, a factory reset, or re-pairing to a
  different network.
- The counter MUST NOT wrap. A sensor that reaches `0xFFFFFFFF` MUST stop
  transmitting. (At one frame per minute this takes over 8000 years.)

### 8.2 Persistence by reservation

To avoid writing flash on every frame, a sensor reserves counter values in
blocks:

1. Flash holds `reserved`, the first counter value not yet reserved.
2. Before using a value `v` where `v >= reserved`, the sensor MUST write
   `reserved = v + B` to flash and confirm the write.
3. On boot, the sensor MUST set its next counter to the stored `reserved` and
   then reserve a new block.

`B` is the block size. It SHOULD be 64. A boot therefore skips up to `B` values,
which is harmless.

`reserved` MUST survive a factory reset.

### 8.3 Retransmission

A confirmed uplink that is not answered is retransmitted as exactly the same
bytes: same `fcnt`, same tags, same ciphertext. It is not a new frame and does not
use a new counter value, but it is a new transmission: the first retry comes at
least 4 seconds after the original (08 section 5). Proxies and the server
therefore tell transmissions apart by time, not by bytes: copies received within
2 seconds of a transmission's first copy are that transmission, and a later copy
is a retransmission that MUST reach the server and be answered again (section
8.5).

### 8.4 Downlink counters

Downlinks under the root key set and under the session key set have separate
counters, because a counter only has to be unique per key.

**Root downlink counter.** The server keeps a root downlink counter per device
(`dev_eui`) for the `DOWNLINK` frames that answer `JOIN`.

- It starts at 1 for the first `KEY_EXCHANGE` the server ever builds for the
  device and increases by one for each new one.
- The server MUST NOT reset it: not on `JOIN`, not when re-pairing, not when the
  device is removed or discarded. It MUST keep it, with the same reservation
  scheme as 8.2, for as long as it may pair the device again (07 section 2.2).
- A `KEY_EXCHANGE` resent for a retransmitted `JOIN` is the identical frame and
  does not use a new value (04 section 4.2).

**Session downlink counter.** The server keeps a downlink counter `fcnt_down` per
`k_session`. It starts at 1 for the first downlink under a new `k_session`,
increases by one per downlink frame it builds, and is persisted with the same
reservation scheme as 8.2. A new `k_session` is a new key, so its counter starts
again at 1.

**Sensor floors.** A sensor keeps, in non-volatile storage, the last accepted
counter value for each key set:

- the *root floor*, for downlinks under the root key set. It survives `JOIN`,
  pairing, `LEAVE` and re-pairing. Only a factory reset sets it back to 0 (04
  section 6.2).
- the *session floor*, for downlinks under the session key set. The sensor sets
  it to 0 when it derives a new `k_session` (04 section 4.4, step 4).

A sensor MUST discard a downlink whose counter is not greater than the floor of
the key set it was sent under.

### 8.5 Server acceptance of uplinks

For each device the server keeps `last_fcnt`, the highest accepted uplink
counter, and a record of which of the 15 counter values below it
(`last_fcnt - 15` to `last_fcnt - 1`) were received. Each frame gets one of four
results:

- `accept`: `fcnt > last_fcnt`. Accept, and update `last_fcnt`. Any gap is
  allowed.
- `accept_late`: `last_fcnt - 16 < fcnt < last_fcnt` and not yet received.
  Accept (late arrival).
- `duplicate`: `fcnt == last_fcnt`, or a value in the window that was already
  received. Treat it as a retransmission or replay and do not deliver it again.
  If it is a retransmission (section 8.3) of a confirmed type, the server MUST
  answer it again, within the limits of 07 section 4, step 5, so a sensor that
  missed the first answer stops retrying.
- `too_old`: `fcnt <= last_fcnt - 16`. Drop it; the server no longer knows
  whether it was received.

A frame is accepted only after its MIC verifies.

## 9. Uplink payload

```
Offset  Size  Field
0       1     uflags
1       N     readings (03, Payload v1), 0 <= N <= 63
```

`uflags` bits:

| Bit | Name | Meaning |
|---|---|---|
| 0 | `DL_ACK` | The sensor accepted a downlink containing commands since its previous uplink |
| 1 | `TIME_UNSURE` | The sensor's clock has not been set by a downlink since boot |
| 2-7 | reserved | MUST be 0 when sent, MUST be ignored when received |

## 10. Downlink payload

### 10.1 Layout

```
Offset  Size  Field
0       4     reply_to     fcnt of the uplink this downlink answers
4       4     server_time  server's Unix time when the downlink was built
8       1     dflags
9       M     commands     zero or more commands, M <= 55
```

`dflags` bits:

| Bit | Name | Meaning |
|---|---|---|
| 0 | `PENDING` | The server has more downlinks queued; the sensor SHOULD send an uplink soon |
| 1-7 | reserved | MUST be 0 when sent, MUST be ignored when received |

### 10.2 Sensor acceptance

A sensor MUST accept a downlink only if all of the following hold:

1. It arrived in an RX window of the sensor's most recent uplink.
2. The MIC verifies.
3. `reply_to` equals the `fcnt` of that most recent uplink.
4. Its counter is greater than the floor for its key set (8.4).

Binding every downlink to the uplink it answers means old downlinks cannot be
replayed, even into a sensor that has just been reset.

On accepting a downlink, the sensor:

- MUST set its clock to `server_time`.
- MUST treat a confirmed uplink as acknowledged.
- MUST execute the commands in order.
- MUST set `DL_ACK` in its next uplink if the downlink contained at least one
  command. That is the next new frame, whose `fcnt` is greater than the
  downlink's `reply_to`; a retransmission of an earlier frame (8.3) is unchanged.
  The server binds the acknowledgement to the downlink by that `fcnt` (07
  section 7).

### 10.3 Commands

Each command is a type-length-value entry:

```
cmd_id (uint8) | len (uint8) | args (len bytes)
```

A sensor MUST skip a command it does not know, using `len`. Commands MUST be
idempotent, because the server re-sends any command it has not seen
acknowledged with `DL_ACK` (07 section 7).

| `cmd_id` | Name | Args | Effect |
|---|---|---|---|
| `0x01` | reserved | | Formerly `SET_NETWORK`; MUST NOT be sent |
| `0x02` | `SET_HEARTBEAT` | `uint16` minutes, 1-1440 | Change the heartbeat interval |
| `0x03` | `LEAVE` | none | Erase `k_session`, return to unpaired state (counters are kept) |
| `0x04` | `KEY_EXCHANGE` | `server_pub` (32) | Complete the X25519 exchange (5.3) and switch to the session key set |
| `0x05` | `NOP` | none | Nothing. Like any command, it makes the sensor set `DL_ACK` (10.2), so a server can learn whether a downlink was accepted |
| `0x06`-`0x3F` | reserved | | Future network commands |
| `0x40`-`0x7F` | application | | Defined in 03 (Payload v1) and by device profiles |
| `0x80`-`0xFF` | reserved | | |

## 11. Bootstrap frames

`JOIN` and `SYNC` use bootstrap tags (section 6.1), derived from the frame
counter rather than the clock, because the sensor either has no session yet or
does not trust its clock.

### 11.1 `JOIN`

Sent by a sensor that has no session, normally when the user presses its button
during pairing. It is encrypted under the root key set, with the root key set's
bootstrap tag. Its payload is:

```
uflags (1, TIME_UNSURE set) | sensor_pub (32)
```

The server answers with a `DOWNLINK` under the root key set, with the `JOIN`'s
tag, containing `KEY_EXCHANGE`. Nothing else may be sent under the root key set.
The full pairing procedure is in 04.

### 11.2 `SYNC`

Sent under the session key set, with the session key set's bootstrap tag, by a
paired sensor:

- whose clock is unknown, for example after the batteries were removed;
- that has had no answer to confirmed uplinks for a long time (threshold in 08
  section 6).

Its payload is `uflags` optionally followed by readings. The server answers with a
`DOWNLINK` carrying the `SYNC`'s tag. Its `server_time` sets the sensor's clock,
after which the sensor uses normal tags again.

### 11.3 Server identification of bootstrap frames

The server keeps the bootstrap tags of its paired devices in its tag table (07
section 3): for each, the block holding the last `fcnt` it accepted and the 2
blocks after it. A bootstrap frame whose tag is in the table is identified like a
normal frame.

A bootstrap frame whose tag misses the table, but that one of the server's own
proxies heard, is identified by trial decryption:

- For `JOIN`: the server tries the root key set of each device that is waiting to
  be paired (`SCANNED` or `EXCHANGED`, 04 section 4.2). A `JOIN`'s counter is
  unknown to the server, so `JOIN` is always found this way.
- For `SYNC`: the server tries the session key set of each device that is paired
  or in the middle of pairing. This finds a sensor whose counter is far past the
  last one the server saw, for example one that rebooted many times out of range.
- The server MAY instead derive the bootstrap tag of each candidate from the
  frame's clear `fcnt` and compare it.
- The server MUST limit how many bootstrap frames it identifies this way per
  minute, so that a flood of bootstrap frames cannot use unbounded CPU. 50 per
  minute is RECOMMENDED.

A frame with a normal tag that misses the table is not tried at all.

### 11.4 Federation limit (informative)

`JOIN` is never federated: its tags derive from `k_root`, which anyone who has
seen the pairing code holds. Pairing therefore always needs one of the owner's
own proxies within range of the sensor. `SYNC` has a real tag, so federation can
route it to its owner (09).

## 12. Proxy rules

A proxy has no keys. For each received LoRa packet it MUST:

1. Discard it if it is shorter than 23 or longer than 86 bytes, if `magic` is not
   `0xC5`, or if `version` is not 1.
2. Discard it if its type is `0x0` or a downlink type (`0x8`-`0xF`). Proxies hear
   each other's downlinks and MUST NOT forward them.
3. Discard it if the exact same bytes were forwarded within the deduplication
   window (RECOMMENDED 2 s). The window MUST be shorter than 4 seconds, so a
   retransmission (section 8.3) is always forwarded.
4. Forward it unchanged, with reception metadata, as defined in 05 (Proxy
   envelope).

Proxies MUST forward uplink types they do not recognize (`0x7`), so new frame
types work without proxy updates.

## 13. Security considerations

| Concern | How v1 handles it |
|---|---|
| Forged frames | AES-CCM with a 64-bit tag and a per-device key |
| Replay of uplinks | Counter rules in 8.5 |
| Replay of downlinks | `reply_to` binding and downlink counter (10.2) |
| Nonce reuse | Counters never repeat (8.1, 8.2, 8.4); direction byte separates uplink and downlink. One residual case is accepted: see 13.1 |
| Tracking a device over time | Hourly tags, and per-block bootstrap tags, derived from the device's own key; `dev_eui` never in the clear |
| Grouping the devices of one network | Nothing in a frame is shared between devices: there is no network tag (section 5.2) |
| Claiming another device's tags | A tag is a public-key fingerprint, so proving it needs `k_dev_tag` (section 6.1) |
| Linking via counter values | Not addressed in v1. `fcnt` is in the clear and increases steadily, so an observer can link a device's frames across epochs by counter continuity. Federation widens who can observe it (09 section 9). A future version may mask it. |
| Key compromise | Per device. A leaked pairing code lets an attacker who is present during a future pairing interfere with it, but does not reveal any past or future session that it did not take part in (5.3). |
| Second-hand devices | A change of owner requires a factory reset (04 section 6.3), which also erases the previous owner's keys. A previous owner who kept the pairing code cannot read traffic after the device is paired again. They can attempt an active attack during that pairing, from within radio range, since `JOIN` is never federated (11.4). Owners who need protection from that SHOULD re-flash `k_root` on second-hand or untrusted devices. |
| Proxy dropping frames | Out of scope for the frame format; handled by path diversity and supervision (07) |

The 64-bit MIC gives a forgery probability of 2^-64 per attempt, which is far
below what LoRa airtime allows an attacker to try.

### 13.1 Root nonce reuse after a factory reset

One server never encrypts two different plaintexts under the same root key and
nonce: its root downlink counter never resets (8.4), and a retransmitted `JOIN`
gets the identical frame back (04 section 4.2). Two servers do not share a
counter, though. After a factory reset the sensor's root floor is 0, and a new
owner's server, or a server that lost its counter (reinstalled, or restored from
an old backup), starts again at low values that an earlier server may already
have used under the same `k_root`. The uplink counter is not affected, because it
survives a factory reset (8.2).

This residual reuse is accepted:

- Only `KEY_EXCHANGE` frames are ever sent under the root key set (11.1). Two of
  them under one nonce reveal the XOR of their plaintexts: `reply_to`,
  `server_time`, `dflags` and a server ephemeral public key. None of these is
  secret. The security of `k_session` rests on the ephemeral private keys, which
  never leave either side (5.3).
- Knowing the keystream for a nonce does not let an attacker forge a frame: the
  CCM tag is a CBC-MAC under `k_enc`, and a forged `KEY_EXCHANGE` would also have
  to answer the sensor's current `JOIN` (10.2) and exceed its root floor.
- The only party that can make a server reuse values is one that already holds
  `k_root`, such as a previous owner, and they can already attempt an active
  attack on a pairing (13).

## 14. Test vectors

`vectors/frame-v1.json` contains root and session key sets, the X25519 exchange,
and in `tags` the `index`, `seed`, `pub` and `tag` of section 6.1: normal tags of
the session key set for three epochs, and bootstrap tags of both key sets at
`fcnt` 1, 64, 65 and 129 (blocks 0, 0, 1 and 2). Its eight frames cover the whole
shortened pairing (`JOIN`, `KEY_EXCHANGE`, the first session uplink and its
answer, 04 section 4.4), a `NOP` followed by `DATA_CONFIRMED` with `DL_ACK`, a
plain acknowledgement, a `HEARTBEAT`, and a `SYNC` after a reboot.
`KEY_EXCHANGE` is root downlink 1; the answer that carries `NOP` and the plain
acknowledgement are session downlinks 1 and 2 (8.4).

Its `invalid` frames, all under the session keys, must be discarded: a flipped MIC
bit and an uplink sealed with the downlink direction byte (section 7), lengths 22
and 87, a wrong magic and version 2 (section 3), and type `0x0` (section 4). Apart
from the first two, each carries a valid MIC for its own header, so only the
named rule rejects it. `proxy_discards` says whether a proxy's keyless checks
(section 12) catch it; the MIC failures it forwards.

```

server ephemeral private = b0b0...b0b1 (31 bytes of b0, then b1)
time    = 1795226400 (2026-11-21T02:00:00Z), epoch 498674
```

X25519 private keys are used as given; RFC 7748 clamping happens inside X25519.
